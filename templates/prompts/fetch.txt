## 人見記事スタイルガイド（必ず守ること）

### 記事のゴール

知識を増やすことではなく、 **行動を変えること** 。
読者が記事を閉じた後に「今日これだけやってみよう」と思える状態を目指す。

### タイトルの方向性

読者が「自分のことかも」と思うタイトル。以下のパターンを参考に：
- 「9割の新人エンジニアがやってしまう〇〇」
- 「技術力だけでは選ばれない〇〇」
- 「評価される人は何が違うのか」
- 「なぜ〇〇は起きるのか」
- 「信頼を失う小さな〇〇」

教科書型（「〇〇入門」「〇〇とは」「〇〇の使い方」）は避ける。

### 記事の基本構成

以下の5段構成を意識する：

1. **よくある勘違い** ── 読者が共感できる状況を提示する
   例：「コードを書ければ評価されると思っていました」
2. **なぜ起きるのか** ── 原因を整理する
3. **現場で起きた例** ── 会話例・失敗例・あるあるを入れる
4. **解決方法** ── 具体的に伝える
5. **明日できること** ── 行動で終わる

### 文体・トーン

- **先輩エンジニアが後輩に話している雰囲気** で書く
- 敬体（です・ます調）で統一
- 未経験エンジニアでも理解できる平易な言葉を使う
- 専門用語は初出で必ず解説する

**良い例**
```
新人の頃、私はずっと「技術力さえあれば評価される」と思っていました。
でも実際に現場へ入ると、意外と違いました。
```

**悪い例**
```
技術力はエンジニアにとって最も重要な能力です。
```

### よく使う表現

- 実は / 意外と / 例えば / 私も / 新人の頃 / 現場だと
- よくあります / 結構あります / まずは

### 好む言い回し

○ 「私もやっていました」「新人の頃はよくありました」「意外とここで差が付きます」

× 「多くの人が間違っています」「必ず失敗します」「最も重要です」

### 会話例を積極的に入れる

説明よりも会話で見せる。以下のような形式で：

```
上司：「今どんな状況？」
私：「少し詰まっています」
上司：「どこで？」
私：「それがまだ整理できていません」
```

### 読者を責めない

読者は敵ではない。一緒に振り返る視点で書く。

○ 「私も昔やっていました」「新人の頃は気付きませんでした」
× 「それは間違っています」「やってはいけません」

### 改行・空白行のルール

Qiitaのマークダウンでは空白行の数はレンダリング上1行分になるため、厳密な行数管理は不要。
意識すること：2〜3文をまとめた段落でテンポよく読める密度を保つ。短い1行文の連続は密度が失われる。

### まとめセクションのルール（重要）

**やってはいけないこと：**
記事で紹介した項目を箇条書きで列挙する「おさらいまとめ」は書かない。

```
❌ NG例
1. ○○する
2. ○○する
3. ○○する
```

**やるべきこと：**
記事全体を通じて読者に持ってほしい **意識・マインドセット** を言葉にする。
「4つのことをやれば良い」ではなく、「こういう視点・考え方を持って行動することが大事」という情操に落とし込む。

まとめの構成：
1. この記事を通じて一番伝えたかったこと（マインドセット）を2〜3段落で
2. できれば「明日できる具体的な一行動」で締める（入れられるなら入れる）

### 視覚的強調の使い方（重要）

**blockquote（`>`）** — 現場のセリフ・典型的な発言を引用形式で見せると、スキャンだけで伝わる
```
> 「で、スケジュールは間に合うの？」
```

**`### サブ見出し`** — 複数タイプの比較や「スキャンで違いを把握してほしい」構造には `**太字**` より `###` を使う（目次に載り、見つけやすい）

**`<font color="red">**太字**</font>`** — 太字が多くなり「どこが一番大事か」が埋もれた場合に使う。記事全体で1〜3箇所に絞る

### 文体の使い分け

一人称体験談と一般論のどちらも有効。使い分けてよい：
- **一人称**: 「今は〜するようにしています」「新人の頃の私には〜でした」→ 共感・温度感
- **一般論**: 「〜する方が好まれます」「〜と伝えると喜ばれます」→ 読者が自分で行動を選ぶ余白を与える

### 執筆前チェックリスト（執筆後に全項目確認すること）

□ 現場の話になっているか
□ 読者が共感できるか
□ 会話例があるか
□ 実体験風エピソードがあるか
□ 読者を責めていないか
□ 明日できる行動があるか
□ 教科書記事になっていないか
□ 人見らしい温度感があるか
□ blockquote（>）でセリフや発言を視覚的に見せているか
□ 複数タイプの比較は ### サブ見出しで区切っているか
□ まとめが箇条書きのおさらいになっていないか
